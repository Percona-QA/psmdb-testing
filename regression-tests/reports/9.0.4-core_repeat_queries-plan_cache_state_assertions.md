# Plan-cache state assertions are incompatible with repeated reads

Environment: PSMDB 9.0.4-1.

`cbr_plan_in_cache_cbr_disabled.js`, `plan_cache_distinct.js` in `core_repeat_queries` — **Test/runner mismatch** — both tests assume that each explicit query advances the plan cache once. The suite imports `jstests/libs/override_methods/rerun_queries.js`, which executes every eligible read command three times and returns only the final result. It intentionally creates, activates and uses cache entries within one apparent query.

## Reproduction and control

Both tests ran sequentially with one worker, a 1 GB WiredTiger cache, 2 CPUs and an 8 GB memory limit:

```bash
/opt/venv/bin/python buildscripts/resmoke.py run \
  --suites=core_repeat_queries --installDir=/usr/bin \
  --jobs=1 --continueOnFailure --testTimeout=1800 \
  --storageEngineCacheSizeGB=1 --dbpathPrefix=/data/core-repeat \
  --reportFile=/tmp/core-repeat.json \
  jstests/core/query/plan_cache/plan_cache_distinct.js \
  jstests/core/query/cbr_plan_in_cache_cbr_disabled.js
```

- `plan_cache_distinct.js`: FAIL in 0.20 seconds. After clearing the cache and issuing the first distinct query, `assertDistinctUsesPlanCacheCorrectly()` expects `statsA[0].isActive` to be false. The override has already repeated the query and activated the entry; its actual value is true.
- `cbr_plan_in_cache_cbr_disabled.js`: FAIL in 2.99 seconds. After adding 100000 documents to trigger replanning with CBR disabled, the test expects the first two explicit query iterations to leave the new entry inactive while its works threshold increases. Hidden repeats already activate it. The assertion reports `Incorrect active-ness state` with `isActive: true` and `works: 34503`.

A disposable copy of the effective suite configuration removed only the `rerun_queries.js` import, preserving fixture options, other setup and hooks. Both full tests passed: CBR test in 3.60 seconds and distinct test in 0.73 seconds. Baseline resmoke exited 1; control exited 0. Both actual tests executed in each run; hook/setup entries are not additional tests. These are cache-state assertion failures, not evidence that ordinary query results are incorrect.

## Required PSMDB test change

Add `does_not_support_repeated_reads` to the existing tags in:

- `jstests/core/query/cbr_plan_in_cache_cbr_disabled.js`.
- `jstests/core/query/plan_cache/plan_cache_distinct.js`.

The maintained `repeat_queries.excluded_files` definition in `buildscripts/resmokeconfig/matrix_suites/overrides/repeat_queries.yml` already excludes this tag. No generated YAML edit is needed. This preserves the suite's repeated-read behavior and the tests' precise cache-transition checks in compatible suites.

The `core_repeat_queries` mapping states that this standalone diagnostic suite is combined into `core_min_batch_repeat_queries_multiplan_single_solutions_ese_gcm` for Evergreen. The combined mapping also uses the repeated-read exclusion definition. Actual task/variant inclusion could not be verified because referenced Evergreen components are absent from both matching checkouts.

The compared tests, override and exclusion definition match the local mongo baseline; this is a shared test annotation/configuration mismatch, not an established Percona-specific planner defect. The regression list now excludes both tests only in `core_repeat_queries`, assigning `does_not_support_repeated_reads` through `generated_resmoke_config/repeated_reads_tags.yml`. The maintained PSMDB test sources remain unchanged; their missing tag still needs to be added there.

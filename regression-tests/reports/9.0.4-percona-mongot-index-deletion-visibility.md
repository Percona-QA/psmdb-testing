# percona-mongot: index deletion is visible to management before query-catalog removal

## Summary and environment

PSMDB 9.0.4-1; percona-mongot 1.70.3, and 1.70.5 for scenario 1.

**Classification:** Potential percona-mongot deletion-visibility/contract issue, reproduced through two tests. Both observe queries using an index after its deletion has been acknowledged and its management listing is empty. Query-catalog removal follows asynchronously. This is a shared observed mechanism; the exact causal Java change and whether the API promises synchronous query invisibility remain unresolved.

The symptoms differ: `mongot_indexed_views_upgrade_downgrade.js` rejects `$search` because the deleted index is still resolved as a vector index; `ranked_fusion_on_search_view.js` compares two equivalent aggregations across the deletion transition and obtains 28 versus 10 documents. A five-second post-drop delay makes both scenarios pass in the recorded controls. The delay is diagnostic evidence, not a permanent fix.

Recorded runs used one worker, a 1 GB WiredTiger cache, two CPUs and 8 GiB RAM. Data storage was initially empty tmpfs to avoid the separate 85% disk-utilization blocker. Storage paths must cover both fixture dbpaths and cwd-relative mongot `data/config_journal_*` directories.

## Scenario 1: mongot_indexed_views_upgrade_downgrade.js

Test: `jstests/with_mongot/e2e/views/mongot_indexed_views_upgrade_downgrade.js`.

Suite: `mongot_community_fixture_e2e_single_node`, using an authenticated single-node replica set and gRPC connections to percona-mongot.

### Steps to reproduce

1. Use PSMDB 9.0.4-1 and percona-mongot 1.70.3 or the supplied 1.70.5 package. Install the fork at the fixture's mongot-community executable location. For 1.70.5 the tested package was:
   https://downloads.percona.com/downloads/TESTING/ps4m-1.70.5/percona-search-mongodb-1.70.5-linux_x86_64.tar.gz
2. Provide fresh mongot data storage with sufficient free capacity. Completed reproductions used an empty 2 GiB tmpfs; ordinary storage initially hit the package's 85% disk-utilization threshold, a separate blocker.
3. Run the unchanged test:

```bash
python buildscripts/resmoke.py run \
  --suite=mongot_community_fixture_e2e_single_node --installDir=/usr/bin \
  --jobs=1 --testTimeout=1800 --storageEngine=wiredTiger \
  --storageEngineCacheSizeGB=1 \
  jstests/with_mongot/e2e/views/mongot_indexed_views_upgrade_downgrade.js
```

Use two CPUs and 8 GiB RAM, as in the recorded runs. The fixture uses a single-node replica set, authentication and gRPC communication with percona-mongot.

### Expected and actual

The test drops a vectorSearch index named index, waits until the listing is empty, and later issues $search while repeating an FCV/view scenario. Query resolution should not select the logically deleted vector index; alternatively, the API must expose a documented readiness condition the test can await.

Actual response:

```text
Cannot execute $search over vectorSearch index 'index'
code: 8 (UnknownError)
```

The drop is acknowledged and no index is listed, but name/type resolution still finds the vector index. The failure occurs during the second upgradeDowngradeFCV invocation after downgrade to FCV 8.0.

### Evidence

For percona-mongot 1.70.3, drop receipt was logged at 03:08:32.712, the query failed by 03:08:32.923, and IndexActions logged catalog removal at 03:08:33.485. For 1.70.5 the corresponding times were 03:36:13.673, 03:36:13.863 and 03:36:14.378. Times are the original UTC-04:00 log times; the significant evidence is event ordering.

The isolated 1.70.3 test failed in 6.48 seconds; the 1.70.5 test failed in 6.54 seconds. In a 1.70.3 control, adding only sleep(5000) immediately after vector-index deletion made the test pass in 22.01 seconds. The delay is causal timing evidence, not a permanent fix.

### Separate FCV cleanup problem

An assertion can leave FCV at 8.0. A full recorded run then had 59 later failures; three representative downstream tests passed on a fresh FCV 9.0 fixture. This supports a cascade but does not establish every later failure's cause. Restore FCV in a guaranteed finally block in the PSMDB test. The remaining full suite has not been proven to pass.

The deletion-contract interpretation and exact patch origin remain unresolved. No percona-mongot fix was implemented or validated.


### Product-path control

Keep this as a potential percona-mongot issue: the failure was reproduced with the Percona fork, while the recorded community-mongot control passed in 5.74 seconds. The compared management paths differed (AicDropSearchIndexCommand versus FileBackedDropSearchIndexCommand). This is product-path evidence, not an isolated Percona patch: matching-revision Java source comparison was not performed and a shared implementation origin remains possible. FCV restoration in the PSMDB JS test is a separate test-isolation concern, not established as Percona-specific.

## Scenario 2: ranked_fusion_on_search_view.js

Test: `jstests/with_mongot/e2e/hybridSearch/ranked_fusion_on_search_view.js`.

Reproduced suite: `mongot_community_fixture_e2e_sharded_collections`, with two shards, three mongos processes and gRPC search connections. Flakiness in `mongot_community_fixture_e2e_single_node` was reported but was not reproduced locally in this investigation. The image's test and hybrid-search helper matched the working checkout byte-for-byte.

### Problem and impact

An acknowledged search-index deletion and an empty `$listSearchIndexes` response do not establish that the index has disappeared from percona-mongot's query catalog. Two equivalent rank-fusion aggregations can execute across that asynchronous transition and return different numbers of documents. This makes a correctness comparison flaky; the observed mismatch is not merely a change in ordering or floating-point scores.

The unchanged test passed once in isolation. A subsequent repeat-five invocation passed its first execution and failed its second; remaining repetitions were not executed after the failure. The failed execution took 5.87 seconds:

```text
expected and actual array lengths are not equal.
Expected array len = '28' and actual array len = '10'.
```

The failure is in the first match-only rank-fusion scenario, through `runHybridSearchOnSearchViewsTest()` and `assertDocArrExpectedFuzzy()`. It occurs before the later cases deliberately expecting an error for mongot input pipelines on search views. Resmoke exited 1; the failed shell report recorded exit code 253.

### Reproduction steps

1. Install percona-mongot 1.70.3 at the fixture's `mongot-community/mongot` location under `/usr/bin`, using the package configured in the suite-list setup:
   `https://downloads.percona.com/downloads/percona-search-mongodb/percona-search-mongodb-1.70.3/binary/tarball/percona-search-mongodb-1.70.3-linux_x86_64.tar.gz`.
2. Provide clean storage for the fixture dbpaths and the cwd-relative `data/config_journal_*` directories. Avoid disk-watermark throttling.
3. From the PSMDB source directory, run:

```bash
/opt/venv/bin/python buildscripts/resmoke.py run \
  --suites=mongot_community_fixture_e2e_sharded_collections \
  --installDir=/usr/bin --jobs=1 --repeatTests=5 \
  --testTimeout=1800 --storageEngineCacheSizeGB=1 \
  --reportFile=/tmp/ranked-repeat.json --dbpathPrefix=/data/ranked-repeat \
  jstests/with_mongot/e2e/hybridSearch/ranked_fusion_on_search_view.js
```

The failure is timing-dependent; a single execution may pass.

### Relevant test and management behavior

`jstests/with_mongot/e2e_lib/hybrid_search_on_search_view.js` creates 50 documents, creates text/vector indexes and creates search-backed views. At the bottom of the module it executes:

```javascript
dropSearchIndex(coll, {name: searchIndexFoo});
dropSearchIndex(coll, {name: vectorSearchIndexV});
```

These top-level statements run during import, before the calling test starts its scenarios. The exported helper then compares equivalent pipelines over the collection and a view:

```javascript
const expectedResultsNoSearchIndexOnView = coll.aggregate(
    hybridSearchPipelineWithViewPrepended,
);
const viewResultsNoSearchIndexOnColl = searchView.aggregate(hybridSearchPipeline);
assertDocArrExpectedFuzzy(
    expectedResultsNoSearchIndexOnView.toArray(),
    viewResultsNoSearchIndexOnColl.toArray(),
);
```

`dropSearchIndex()` in `jstests/libs/query_integration_search/search.js` forwards/replicates the management command and verifies an empty index listing. It does not separately wait for percona-mongot query-catalog invalidation.

The failing run recorded vector-index drop receipt at 16:00:33.859 and 16:00:33.932 on the two shard mongot processes. `IndexActions` logged removal from the query catalogs at 16:00:34.505 and 16:00:34.785. The comparison failed by 16:00:34.739, before the latter removal. These are original UTC-04:00 log times. The interval allows query visibility to differ between shards and between successive aggregations.

### Controls and attribution

Adding only `sleep(5000)` after both top-level drop calls, in a disposable helper copy, made five sequential executions pass: 21.80, 17.10, 17.87, 15.62 and 17.88 seconds. Resmoke exited 0. This is a diagnostic timing control, not a proposed permanent sleep-based fix.

With the original helper restored, `mongot_community_e2e_sharded_collections` using mongot-localdev passed three sequential executions; the complete invocation took 48.01 seconds and exited 0. The suite uses the same shard/router topology and gRPC settings; it launches `MongoTFixture`/mongot-localdev instead of YAML-configured `MongoTCommunityFixture`/percona-mongot. No exact matched Java-source revision comparison was performed.

The evidence supports a percona-mongot deletion-visibility/integration issue. It does not identify an exact causal Java patch or establish that the management API contract requires synchronous invalidation. The test also assumes a stable post-drop query state too early. The same deletion-visibility mechanism is observed in scenario 1.


## Shared investigation and possible fixes

Inspect percona-mongot's `AicDropSearchIndexCommand`, `CommunityMetadataUpdater`, `DesiredConfigStateUpdater` and `IndexActions`. Logs identify these paths; Java source was not inspected and no exact defective statement or matched-revision fork diff was established.

- Trace management acknowledgment, tombstone propagation, index listing and query name/type resolution. If drop completion promises query invisibility, remove or invalidate query-catalog entries before acknowledging deletion.
- If deletion is intentionally asynchronous, expose a deterministic query-invisibility readiness condition and await it in `jstests/libs/query_integration_search/search.js`. An empty `$listSearchIndexes` response alone was insufficient in both scenarios. Check the fixture's `internalListAllIndexesForTesting` behavior.
- Validate a reduced create-vector/drop/list/search sequence to separate deletion semantics from FCV/view interactions. This reduction has not been executed.
- For the rank-fusion helper, review moving top-level cleanup after all scenarios. That changes the intended index state and needs validation before adoption.
- Independently add guaranteed FCV restoration to the scenario-1 test's `finally` block to prevent cascading failures.

## Status and validation criteria

The regression list excludes `mongot_indexed_views_upgrade_downgrade.js` only in `mongot_community_fixture_e2e_single_node`. It excludes `ranked_fusion_on_search_view.js` in both Percona fixture suites. Both exclusions use the generated `requires_synchronous_mongot_index_drop` tag. mongot-localdev entries remain enabled. No maintained PSMDB source or fixture fix was applied.

Re-enable after the deletion-readiness contract or catalog invalidation is corrected and repeated sharded/single-node runs confirm stable query visibility. Validate both scenarios and FCV restoration after an intentional assertion failure. Finite passing controls do not prove that every race is eliminated; the entire remaining suite was not validated.

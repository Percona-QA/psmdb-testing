PSMDB 9.0.4-1.

Suite `concurrency_sharded_stepdown_terminate_kill_primary_with_balancer_and_config_transitions_and_add_remove_shard`.

**Classification:** shared FSM/hook synchronization failure. The maintained suite and workload match the supplied upstream server checkout.

**Failure:** the FSM runner waits for acknowledgement from its background hooks after worker execution. Its 90-second wait expires with `thread action still in progress` while `ContinuousAddRemoveShard` is still removing a shard. The recorded old-API removal completed after 134.95 seconds. No distinct-result assertion was observed.

**Reproduction:** run `jstests/concurrency/fsm_workloads/query/distinct/distinct.js` in this suite with `--repeatTests=10 --jobs=1 --storageEngineCacheSizeGB=0.25 --testTimeout=1800`, using 3 CPUs and 7 GiB RAM. The first repetition passed in 56.70 seconds. The second failed in 94.68 seconds with shell exit code 253 and resmoke exit code 1. The remaining eight repetitions were skipped. A preceding single run passed.

```text
assert.soon failed (timeout 90000ms)
thread action still in progress
runWorkloads@jstests/concurrency/fsm_libs/resmoke_runner.js
```

**Required investigation:** align the bounded acknowledgement wait in `jstests/concurrency/fsm_libs/resmoke_runner.js` with transition limits in `buildscripts/resmokelib/testing/hooks/add_remove_shards.py`, identify the hook still running in timeout diagnostics, and investigate slow draining under concurrent stepdowns. The per-test timeout does not extend this internal wait.

**Status:** the entire suite is disabled pending synchronization correction and successful repeated runs with all hooks enabled. Other reported workload failures have no retained logs and have not been attributed to this cause.

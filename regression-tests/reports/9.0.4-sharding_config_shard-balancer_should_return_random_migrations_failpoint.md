# Random migration test in config-shard mode

Environment: PSMDB 9.0.4-1.

`jstests/sharding/balancer_should_return_random_migrations_failpoint.js` in `sharding_config_shard` — **Flaky test; parameter-overwrite hypothesis** — a failure was reported, but the unchanged test passed locally in 151.99 seconds with exit code 0, one worker and a 1 GB WiredTiger cache. The intermittent failure was not reproduced locally.

A possible contributing condition is the loss of the test's fast migration settings. In config-shard mode, `jstests/libs/shardingtest.js` shallowly merges `configOptions` with `rsOptions`. The latter's `setParameter` object contains only the random-migration failpoint and replaces the former's object, discarding `reshardingMinimumOperationDurationMillis: 0` and `balancerMigrationsThrottlingMs: 0`. Slower random migrations may affect the test's bounded waits for collection tracking and placement changes.

Resmoke supplies `reshardingMinimumOperationDurationMillis: 5000` through `buildscripts/resmokelib/testing/fixtures/standalone.py`; startup logs confirmed that value. It does not fall back to the server's 300000 ms default, and it does not trigger the balancer's strictly-greater-than-5000 guard. Successful migrations were observed. Parameter replacement is therefore a hypothesis for timing sensitivity, not a confirmed cause or proof that migrations are blocked.

A possible test adjustment is to supply the same complete parameter object in both `configOptions.setParameter` and `rsOptions.setParameter`, retaining the failpoint and both zero-valued settings. This adjustment has not been tested. The failing assertion and preceding logs are needed to establish causation.

The test remains enabled. No test source or suite-list changes were made.

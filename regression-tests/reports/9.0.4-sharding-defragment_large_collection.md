# defragment_large_collection: PIT ownership-history migration conflict

## Execution

PSMDB version: `9.0.4-1`.

```bash
python buildscripts/resmoke.py run --suite sharding --jobs=1   --storageEngine=wiredTiger --storageEngineCacheSizeGB=0.25   --testTimeout=1800 --reportFile=/work/report.json   jstests/sharding/defragment_large_collection.js
```

Container limits: 2 CPUs, 8 GiB memory. Server startup logs confirm main WiredTiger `cache_size=256M`. This cache limit is per mongod, not a container-wide memory cap.

Random seed: `4760278476629287`. The test selected 7 shards. The first collection had 8 chunks and 1 zone.

Result: FAIL after 102.54 seconds, resmoke exit code 1, JS exit code 253. Resmoke setup/teardown entries passed. The first `runTest(1, "singleCollection")` failed; the later three-collection scenario was not reached.

## Primary cause

The visible assertion is `assert.soon failed (timeout 90000ms)` in `waitForEndOfDefragmentation()` at `jstests/sharding/libs/defragmentation_util.js`, called from the test.

Server logs establish a preceding, repeated migration error:

```
OperationFailed: Command request failed on source shard. :: caused by ::
Data transfer error: migrate failed: ConflictingOperationInProgress:
Migration aborted: committing it would drop point-in-time reachable ownership
history for a chunk only partially covered by source chunk
[{ key: 1000.0 }, { key: 2000.0 }).
Set the allowMigrationsToDropRecipientPITHistory server parameter to bypass this check.
```

The defragmentation policy repeatedly logs `Encountered non-retriable error on migration during collection defragmentation`, then transitions back through `mergeAndMeasureChunks` and `moveAndMergeChunks`. The same migration conflict recurs until the assertion deadline. Thus the reproduced failure is not explained solely by a small cache or insufficient time.

## Supporting source

- `src/mongo/db/s/migration_destination_manager.cpp`, `MigrationDestinationManager::ensurePITHistoryPreserved()`: rejects migrations that would discard reachable recipient ownership history.
- `src/mongo/db/sharding_environment/sharding_runtime_d_params.idl`: `allowMigrationsToDropRecipientPITHistory` defaults to false. Its description explicitly identifies indefinitely retried migrations as a possible condition; enabling the escape hatch can make PIT reads observe incorrect ownership.
- `src/mongo/db/s/balancer/balancer_defragmentation_policy.cpp`: failed migration handling and phase reconstruction.
- `jstests/sharding/libs/defragmentation_util.js`: the completion wait supplies no explicit assertion timeout.
- `src/mongo/shell/assert.js`: default `assert.soon` timeout is 90 seconds outside Evergreen versus 10 minutes with `TestData.inEvergreen`. The external 1800-second test timeout does not override it.

## Required investigation / proposed PSMDB changes

Investigate whether defragmentation can converge while preserving recipient PIT history after this sequence of chunk migrations and merges. The policy should avoid endlessly repeating an unchanged, rejected migration or provide an appropriate recovery path. Inspect ownership-history retention and overlap reconciliation alongside migration/defragmentation ordering.

If this test intentionally does not cover PIT-history preservation and requires the escape hatch, document and scope that requirement in the test's own ShardingTest settings. Do not enable it globally for all sharding suites: it changes ownership-history guarantees. Such a control run has not been performed, so this is a candidate diagnostic option, not a verified fix.

An explicit, justified timeout in the helper would make Jenkins/Evergreen timing consistent, but increasing the timeout alone is not a demonstrated solution to the repeated migration conflict.

## Limits

Only one randomized execution was performed, at the requested 0.25 GiB cache. No larger-cache, longer-timeout or escape-hatch control was run. This result does not prove the cache caused the failure or that every seed fails.

Current Evergreen task/variant component includes are unavailable, so exact upstream run settings remain unverified.

## Follow-up: available Evergreen launch settings

The current `evergreen/resmoke_tests_execute.sh` supplies `--storageEngineCacheSizeGB=1` unless task/variant arguments override it (4 GiB for inMemory), `--jobs=${resmoke_jobs}`, optional shuffle/continue-on-failure, `--staggerJobs=on`, and task/variant metadata including `--taskId`. Additional settings come from `${resmoke_args}`, `${test_flags}`, and `${extra_test_flags}`; their exact sharding task/variant values are unavailable because the referenced component files are missing. Public corresponding raw-file requests also failed to retrieve them; no inference of upstream enablement/disablement follows.

`--taskId` causes resmoke to set `TestData.inEvergreen=true`, which raises the default `assert.soon` deadline from 90 seconds to 10 minutes. This does not enable the PIT-history escape hatch.

Important clarification: `MongoDFixture` already defaults `migrationRecipientPITHistoryToPreserveInSecs=1` and `orphanCleanupDelaySecs=1`. Static inspection confirms these defaults also exist inside the supplied 9.0.4 image. Therefore, simply proposing a one-second recipient PIT window is not a new fix for this environment. The test override computes its cutoff from vector-clock clusterTime; convergence/clock advancement should be considered when investigating the repeated rejection.

No available Evergreen file explicitly sets `allowMigrationsToDropRecipientPITHistory=true`. Its server default is false. Exact task overrides remain unverified, so this absence is not proof of every upstream variant's effective setting. There is no source-backed justification here for adding the escape hatch globally to our suite list.

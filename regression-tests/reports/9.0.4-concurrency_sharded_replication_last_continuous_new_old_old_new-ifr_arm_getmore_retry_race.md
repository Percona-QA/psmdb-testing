## Observations collected during execution

- `analyze_shard_key.js`: JS process completed in 236.68 seconds; subsequent hooks completed.
- `crud/reshard_collection_crud_ops.js`: JS process completed in 59.91 seconds; subsequent hooks completed. The static hypothesis of a mandatory five-minute wait for every resharding operation did not reproduce in this environment.
- `query/ifr_arm_getmore_retry_race.js`: persistent find/getMore commands on both old mongos processes. A local currentOp snapshot on mongos port 20005 showed nine find commands and three getMore commands with the same increasing elapsed times (260, 395, 484, 699 seconds). A distributed currentOp snapshot initially showed no shard-side operations for the test namespace running longer than five seconds. A later direct sample covered config-server port 20000 and one shard primary at port 20003; it was not a direct sample of both shard primaries. Background dbHash/metadata hooks continued completing cycles. Memory remained below 2 GiB at the sampled times.

This identifies the workload and the blocked mongos stage, but does not alone prove the precise C++ cause or that absence of a 9.0 feature is responsible. The test exists in current 9.0 source but not at the exact old binary revision. Old ARM already implements rate-limit retries, but uses a different baton-based retry path from current 9.0. The absence of the JS test in 8.3 is supporting context, not proof of unsupported server functionality.

Exact Evergreen task/variant settings remain unverified: referenced evergreen_yml_components files are absent in the supplied checkout.

All five workloads were selected in one initial invocation. Resmoke stopped further execution after the IFR timeout despite `--continueOnFailure`, so the two remaining workloads required a second invocation after stopping/restarting the same owned container with a fresh fixture. That continuation exited 0 in 27.48 seconds. Its 22 passing entries include two workloads and infrastructure/hooks, not 22 workloads.

At the timeout, resmoke reported no debugger available and began killing/aborting fixture processes. Subsequent background-hook failures are consequences of that shutdown, not evidence that a hook originally caused the workload timeout. The first invocation did not finish writing its JSON report before diagnostic container recovery; its results are supported by the captured executor log. Cleanup was interrupted after approximately another minute, not allowed to run indefinitely.

The persistent queries were observed at 260, 395, 484, 699 and 1002 seconds. This was not merely a slow cumulative suite run. It reproduces a concrete blocking candidate in the mixed 9.0/8.3 fixture; correspondence to the user's Jenkins hang still requires its log.

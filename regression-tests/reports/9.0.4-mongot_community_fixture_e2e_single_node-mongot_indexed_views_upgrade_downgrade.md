# percona-mongot: dropped vector index remains query-resolvable after drop acknowledgement and empty index listing

## Summary

percona-mongot 1.70.3 exposes inconsistent index visibility during deletion: `dropSearchIndex` succeeds and `$listSearchIndexes` reports the index absent, while a subsequent `$search` still resolves that name to the dropped vectorSearch index and fails with:

```
Cannot execute $search over vectorSearch index 'index'
code: 8 (UnknownError)
```

Logs show actual removal from the query catalog occurring after the failed query. The same test passes with the image-provided upstream community mongot (localdev executable). Adding only a five-second diagnostic wait after dropping the vector index makes the community test pass.

This is a confirmed timing-dependent behavior in the tested percona-mongot execution path. Whether it violates the intended deletion contract, and whether it originates in Percona-specific changes rather than shared upstream code, remains to be established.

## Terminology

- **Upstream community mongot**: used by `mongot_community_e2e_single_node`, launched through `MongoTFixture` using the `mongot-localdev/mongot` executable. “Localdev” here names its launcher/package, not a separate product classification.
- **percona-mongot**: Percona’s fork, used by `mongot_community_fixture_e2e_single_node`, launched through `MongoTCommunityFixture` using the `mongot-community/mongot` executable from the Percona Search 1.70.3 package.

The suite names, executable paths and class identifiers retain their exact code spelling. References to the failing implementation in this report mean **percona-mongot**, not upstream community mongot.

## Reproduction

Install the supplied percona-mongot package at `/usr/bin/mongot-community`, then run inside the image:

```bash
python buildscripts/resmoke.py run \
  --suite mongot_community_fixture_e2e_single_node \
  --installDir /usr/bin \
  --jobs=1 \
  --storageEngine=wiredTiger \
  --storageEngineCacheSizeGB=1 \
  --testTimeout=1800 \
  jstests/with_mongot/e2e/views/mongot_indexed_views_upgrade_downgrade.js
```

The test creates and drops search and vectorSearch indexes using the name `index`, then repeats an FCV upgrade/downgrade scenario. During the second invocation of `upgradeDowngradeFCV()`, it downgrades to FCV 8.0 and executes `$search` through an identity view. The previously dropped vector index is still resolved by that query.

Failure location:

```
upgradeDowngradeFCV@jstests/with_mongot/e2e/views/mongot_indexed_views_upgrade_downgrade.js
@jstests/with_mongot/e2e/views/mongot_indexed_views_upgrade_downgrade.js
```

## Actual behavior and decisive timeline

The percona-mongot implementation handles the drop through:

```
com.xgen.mongot.server.command.management.aic.AicDropSearchIndexCommand
```

For the vector index in the failing comparison run:

| Time, UTC-04:00 | Event |
|---|---|
| 03:08:32.712 | `AicDropSearchIndexCommand` receives the drop request. |
| Before the subsequent query | The drop helper returns successfully after verifying an empty `$listSearchIndexes` result. |
| By 03:08:32.923 | `$search` fails with `Cannot execute $search over vectorSearch index 'index'`; the JS test ends in failure. |
| 03:08:33.485 | `IndexActions` logs `dropping index from catalog` for the vector index. |

Thus, a logically absent index remains eligible for query name/type resolution during the metadata propagation interval.

## Comparison and timing control

All runs used the same server binary and test with identical resource limits. Each comparison run started with a clean fixture.

| Execution | JS result | JS duration |
|---|---|---|
| `mongot_community_e2e_single_node`, image-provided upstream community mongot (localdev executable) | PASS | 5.74 s |
| `mongot_community_fixture_e2e_single_node`, percona-mongot 1.70.3 | FAIL | 6.48 s |
| Same percona-mongot suite, only diagnostic `sleep(5000)` immediately after each vector-index drop | PASS | 22.01 s |

Upstream community mongot (localdev executable) uses `FileBackedDropSearchIndexCommand`. In its successful run, the first vector drop was received at `03:06:20.056-0400`, and removal from the catalog was logged at `03:06:20.064-0400`, before subsequent-cycle work.

In the percona-mongot delay control, the corresponding drop was received at `03:09:12.939-0400`; catalog removal occurred at `03:09:13.648-0400`. The next cycle started after the diagnostic wait and passed. FCV restoration also completed successfully.

The five-second wait is diagnostic evidence only. It is not a proposed permanent fix.

## Expected behavior / contract requiring clarification

Clarify what successful deletion and an empty `$listSearchIndexes` result guarantee for subsequent queries.

If the index is already logically deleted, query lookup should not continue selecting it and produce a stale index-type mismatch. Physical resource cleanup can remain asynchronous.

If the supported API intentionally permits this visibility gap, identify a reliable condition that callers and tests can await. In this reproduction, an empty `$listSearchIndexes` result is insufficient to establish query-catalog removal.

## Investigation requested in percona-mongot

1. Inspect `AicDropSearchIndexCommand`: acknowledgement timing, metadata mutation and handling of logically deleted indexes.
2. Trace propagation through `CommunityMetadataUpdater`, `DesiredConfigStateUpdater` and `IndexActions`. Check whether query lookup can continue using an index after management APIs stop listing it.
3. Check tombstone/deletion filtering and cache invalidation in query index resolution, especially reuse of the same name across search and vectorSearch index types.
4. Inspect `$listSearchIndexes` behavior with `--internalListAllIndexesForTesting`, which is passed by the percona-mongot fixture. Determine whether its visibility rules match those used by query execution.
5. Reproduce the shorter sequence without FCV changes: create a vector index, drop it, verify the listing is empty, then immediately issue `$search` using the same name. This reduced reproduction has not yet been executed; it would distinguish ordinary deletion semantics from FCV/view-specific behavior.
6. Compare upstream community mongot and percona-mongot builds from the same source revision. Their management implementations differ, and the localdev build identity was not established. The current comparison identifies the affected fork, but does not isolate a particular Percona patch or establish whether the behavior was inherited from its upstream baseline.

## Regression impact

A completed full percona-mongot-suite run took 325.35 seconds: 129 JS tests, 69 passed and 60 failed. The primary test failed first and left the shared replica-set fixture at FCV 8.0. All 59 subsequent failures occurred after that downgrade; many reported feature-flag, search-on-view or score-sorting restrictions.

Three representative downstream tests passed on a fresh FCV 9.0 fixture:

- `hybrid_search_weights_test.js`: 7.84 s.
- `score_normalization_test.js`: 0.30 s.
- `views/search/max_size_request.js`: 8.89 s.

This supports a cascade caused by the primary failure; it is not proof that every downstream failure has been independently resolved.

Separately, the PSMDB test must restore FCV in `finally` when an assertion fails. Its current cleanup restores a feature flag but does not guarantee FCV restoration. That test-isolation defect amplifies the percona-mongot timing issue into suite-wide failures.

## Evidence limits

- The percona-mongot failure was reproduced in isolation twice, including the matched comparison above. A single delay-control run passed.
- An additional full control excluding the primary test was interrupted after roughly six minutes in `ranked_fusion_on_view.js`; no completed result was obtained for that test. The remaining full suite has not been proven to pass.
- Initial execution on the ordinary Docker filesystem encountered paused initial sync because disk utilization exceeded the percona-mongot package's 85% threshold. The completed comparison and control runs used empty tmpfs storage and did not rely on that blocked environment.
- Exact upstream Evergreen task/variant settings remain unverified: the component files referenced by the current `etc/evergreen.yml` are absent from the checkout.

Timeline (UTC-04:00):

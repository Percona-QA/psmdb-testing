# query_join_optimization_passthrough: incompatible explain tests

## Result

All five user-reported failures reproduced in the supplied 9.0.4 image. All five passed in a control run changing only `internalQueryPlanRanker` from `costBased` to `multiPlanning`. These tests have incompatible assumptions about trial execution and explain error handling in the suite's CBR configuration. They should be excluded from this passthrough rather than changing its intended planner settings.

| `explain_all_plans_execution_stats.js` | FAIL (0.21s) | PASS (0.21s) |

## Exact failures

- `jstests/core/query/explain/explain_all_plans_execution_stats.js`: `did not examine any documents`. An entry in `allPlansExecution` has `nReturned: 0`, `totalDocsExamined: 0` and `totalKeysExamined: 0`, while the test requires nonzero rejected-plan trial statistics. The existing `query_cbr_sampling_jscore_passthrough.yml` already explicitly excludes this test.
- `jstests/core/query/explain/explain_winning_plan.js`: trial `nReturned` is 0 instead of `internalQueryPlanEvaluationMaxResults` (101). The test expects multiplanner trial results rather than CBR explain statistics. The existing CBR sampling suite explicitly excludes it as well.
- `jstests/core/query/explain/explain_execution_error.js`: queryPlanner explain itself fails with code 292, `QueryExceededMemoryLimitNoDiskUseAllowed`, `error while multiplanner was selecting best plan`. The test expects queryPlanner explain to succeed and later executionStats explain to describe the execution failure. The sorting memory limit is the intentional error scenario in the test, not evidence of container OOM.
- `jstests/core/query/expr/expr.js`: explain itself fails with code 14, `TypeMismatch`, `$divide only supports numeric types, not double and date`, during multiplanner selection. The test expects a successful explain carrying failure under executionStats. Earlier expected-error log messages in this test are not its final failure.
- `jstests/core/query/find_with_resume_after_param.js`: explain for an absent clustered RecordId fails with code 211, `KeyNotFound`, during multiplanner selection. The test expects that particular queryPlanner explain to succeed; the underlying find failure is intentional.

The latter three tests, and `explain_winning_plan.js`, already have `does_not_support_multiplanning_single_solutions`. The existing CBR sampling suite excludes that tag with an explanatory comment: CBR can perform multiplanning trials even for a single solution, causing explain itself to fail when a test expects planning to succeed.

## Reproduction environment and limits

PSMDB version: `9.0.4-1`; Docker: 2 CPUs, 8 GiB memory; `--jobs=1 --testTimeout=1200 --storageEngineCacheSizeGB=0.25 --continueOnFailure`; TZ Europe/London. Original join optimization flags, samplingCE and other fixture settings were retained in baseline/control. Both fixture setup and teardown passed. No tests beyond these five were executed.

The five tests are in core and do not require the extensions used by other roots in the full suite. Diagnostic runs therefore used the image binaries without rebuilding extensions or the full suite preparation. Existing list preparation for extensions was preserved.

Exact query task/variant settings remain unverified because referenced `etc/evergreen_yml_components` files are absent locally and the public v9.0 query task include returns 404. No exact upstream task invocation or passing upstream run is claimed.

## Required PSMDB repository change (not implemented)

Update maintained `buildscripts/resmokeconfig/suites/query_join_optimization_passthrough.yml` to mirror its CBR sampling counterpart:

- Add `does_not_support_multiplanning_single_solutions` under selector.exclude_with_any_tags.
- Explicitly exclude `jstests/core/query/explain/explain_all_plans_execution_stats.js` and `jstests/core/query/explain/explain_winning_plan.js` with comments explaining their multiplanner trial-statistics assumptions. The winning-plan file is already covered by the tag, so its explicit file exclusion is optional and mirrors the sibling suite for documentation.

These changes preserve CBR and join-optimization coverage. The external list update is a workaround until the matching PSMDB suite owns the exclusions. No server/test/suite source or Jenkins changes were made.
